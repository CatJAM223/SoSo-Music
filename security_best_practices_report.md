## Статус после исправлений — 19 октября 2026

Три приоритетные проблемы ниже исправлены в рабочей копии:

- media:// обслуживает только файл, выбранный в системном диалоге. Доступ выдаётся через случайный идентификатор и сохраняется в main-процессе между запусками; произвольные пути и query-параметры отклоняются. Обход CSP удалён. Потоковая выдача поддерживает Range и HEAD.

Ранее выбранный фон необходимо один раз выбрать заново в настройках: старые абсолютные пути автоматически не получают разрешение. После нового выбора разрешение сохраняется между запусками.

Ограничение попыток LAN-кода и общая унификация IPC остаются рекомендациями. Сквозная проверка реальной учётной записи Google и длительное прослушивание не выполнялись.

## 1. Высокий приоритет: произвольные локальные пути в media://

Места: src/desktop/main/index.ts:944, :957, :1082, :1096.

Схема зарегистрирована с supportFetchAPI и bypassCSP. extractFilePathFromMediaUrl принимает абсолютные пути, в том числе через query-параметр path. Обработчик проверяет только существование файла, затем передаёт его net.fetch. Не проверяются разрешённый каталог, тип файла или факт выбора файла пользователем. Ответы разрешены для origin null, который используется локальным renderer.

Таким образом, привилегированный обработчик не ограничен медиафайлами. При исполнении вредоносного JavaScript в renderer появляется путь к чтению произвольных доступных процессу локальных файлов. Это условная цепочка: самостоятельный способ внедрения JavaScript и сквозная кража файла в работающем Electron в рамках проверки не воспроизводились. Нельзя утверждать, что любой сайт уже может читать файлы.

Рекомендация: выдавать непрозрачные идентификаторы только явно разрешённым файлам, хранить отображение ID → путь в main, проверять разрешения при каждом запросе; убрать bypassCSP. Одного ограничения расширений недостаточно.

## 2. Высокий приоритет: неподдерживаемый Electron 33

Места: package.json (electron ^33.2.0), package-lock.json:3855 (33.4.11). Установленный пакет также имеет версию 33.4.11.

Поддержка Electron 33 завершилась 28 апреля 2025. Источник: https://releases.electronjs.org/schedule . Приложение загружает удалённые страницы и контент, поэтому поддерживаемый Chromium/Electron здесь существенен для безопасности. Диапазон ^33.2.0 не переведёт приложение на следующую основную версию.

Рекомендация: перейти на поддерживаемую ветку Electron и проверить авторизацию YouTube, встроенные страницы, аудио, preload, оверлей и упаковку. Конкретный эксплойт против установленной сборки не проверялся; окончание поддержки само по себе не доказывает конкретную эксплуатацию.

## 3. Средний приоритет: параллельный запуск LAN-синхронизации оставляет сервер после остановки

Места: src/desktop/main/services/lanSyncServer.ts:44–74; src/desktop/ui/components/modals/SettingsModal.tsx:270, :1148.

start() проверяет this.server до await, но записывает его только после открытия порта. Два пересекающихся вызова оба проходят проверку, создают два сервера и перезаписывают единственную ссылку. stop() закрывает только последний. Обработчик кнопки в интерфейсе не блокирует повторный запуск на время ожидания.

Воспроизведено вызовом Promise.all([sync.start(), sync.start()]) с фиктивной базой. Для проверки bind принудительно ограничивался loopback. Получены два разных порта и два слушателя. После stop(): reportedActive=false, listenersAfterStop=1. Оба тестовых сервера затем закрыты.

При остановленной сессии оставшийся сервер отклоняет запросы через проверку this.server; обход авторизации этим тестом не доказан. Но интерфейс ошибочно сообщает о полном выключении, а сокет остаётся открытым. После нового запуска старый обработчик использует общее состояние новой сессии.

Рекомендация: хранить общий Promise запуска, сериализовать start/stop, корректно отменять незавершённый запуск. Добавить тесты конкурентных start и stop во время start.

## Дополнительные направления улучшения

- index.html:6 разрешает unsafe-inline в script-src. Это ослабление защиты от XSS, а не доказанная XSS. Начальную настройку темы можно вынести в отдельный скрипт.
- Проверка отправителя IPC применяется неравномерно: новые обработчики используют assertMainWindowSender, многие обработчики медиатеки и синхронизации её не вызывают. Стоит унифицировать проверки и ограничить API каждого окна. Доступ сторонней страницы к IPC не доказан.
- LAN-код состоит из восьми цифр; в обработчике нет ограничения частоты неверных попыток. Есть ограничения по локальной сети и времени жизни сессии, поэтому это дополнительное усиление, а не доказанный быстрый подбор.
- Часть тестов проверяет строки исходного кода. Они полезны как структурные проверки, но не заменяют проверки поведения и реальных границ Electron.
