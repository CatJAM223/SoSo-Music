# Совместное прослушивание: первый прототип

В боковом меню между жанрами и медиатекой расположен раздел «Совместное прослушивание». Создание комнаты открывает закрытую сеть плееров. Ведущий копирует приглашение, остальные вставляют его в «Подключиться к комнате». Максимум — восемь участников.

## Что работает

- Комната создаётся с пустой самостоятельной очередью (до 20 ожидающих треков). Любой участник добавляет выбранный трек кнопкой «+» в списках музыки. Нажатие на трек во время участия в комнате также добавляет только этот трек. Личная очередь не импортируется. Ведущий запускает, ставит на паузу, пропускает и удаляет треки; основной плеер и клавиши управления соблюдают те же права. При окончании трека Rust переводит комнату к следующему треку, при окончании очереди останавливает её.
- Каждый участник самостоятельно получает аудио из YouTube Music или SoundCloud, используя свою авторизацию. Поток аудио, cookies, локальные пути и подписанные ссылки не передаются по сети комнаты.
- Rust проверяет команды, ограничивает участников и размеры сообщений, хранит очередь и вычисляет текущую позицию по монотонным часам. Каждый плеер, включая ведущего, получает решение загрузить трек, продолжить, поставить на паузу или скорректировать позицию.
- Погрешность до 1,2 секунды допускается, более крупное расхождение исправляется перемоткой. Это прототип синхронизации, не режим для двух колонок в одной комнате.
- При уходе ведущего комната закрывается. При потере соединения гость ставит воспроизведение на паузу. Можно повторно войти по приглашению, пока ведущий остаётся в комнате.
- Если интерфейс ведущего перестаёт присылать состояние на четыре секунды, Rust ставит комнату на паузу. Живое сетевое соединение само по себе не считается признаком работающего плеера.
- Изменения очереди приходят в плеер гостя без перезагрузки текущего трека. Порядок хранится на сервере; личные shuffle, crossfade и повтор участников не определяют порядок комнаты.
- Вход в комнату на паузе выбирает нужный трек и позицию без запуска аудио. При смене комнаты пересоздаётся привязка синхронизации к участнику; события завершённого подключения не восстанавливают старую комнату.
- Приглашение содержит адрес подключения и случайный 128-битный ключ доступа. Его следует передавать только участникам.

## Архитектура

`native/listening-rooms` — единственное ядро комнат: TCP/WebSocket, WSS-клиент, ретранслятор, авторитетное состояние ведущего, проекция времени, проверка входных данных и выбор действия синхронизации.

`src/desktop/main/services/listeningRooms.ts` запускает нативный процесс и связывает JSON-строки с IPC. Доступ разрешён только основному окну приложения. В preload выставлены только запросы комнат и подписка на состояние.

React отображает комнату и адаптирует решения Rust к существующему PlaybackEngine. TS не содержит альтернативного сетевого сервера или алгоритма синхронизации.

## Локальная сеть

При создании выберите «Локальная сеть» и адрес нужного сетевого интерфейса. Rust запускает встроенный ретранслятор на этом интерфейсе и свободном порту. Другому устройству нужен доступ к этому адресу через домашнюю сеть или уже настроенную VPN. Windows может запросить разрешение входящих соединений.

Этот режим использует незашифрованный WebSocket внутри доверенной LAN/VPN. Интернет-подключение по обычному публичному `ws://` отклоняется.

## Автоматическое соединение через интернет

Режим «Через интернет» создаёт встроенную комнату и зашифрованную конечную точку iroh на Rust. Ведущий отправляет приглашение, участник вставляет его — вводить адрес сервера и настраивать VPN не нужно. Соединение устанавливается с помощью публичных ретрансляторов n0, затем iroh пытается перейти на прямое соединение с обходом NAT. Если прямой путь недоступен, трафик остаётся на ретрансляторе. Никакой VPN-адаптер Windows не устанавливается.

Приглашение содержит публичный ключ конечной точки, адрес публичного ретранслятора и случайный секрет комнаты. До доступа к протоколу комнаты участник доказывает знание секрета внутри шифрованного канала. Повторная проверка членства и полномочий остаётся в Rust-сервере комнаты. Транспорт не предоставляет произвольный TCP-прокси: он пересылает только соединение к loopback-серверу этой комнаты. Число одновременных рукопожатий ограничено; ожидание соединения и закрытие имеют таймауты. Публичная DNS-публикация отключена; информация передаётся приглашением.

Публичная сеть n0 бесплатна, имеет лимиты и не гарантирует доступность: https://www.iroh.computer/services/hosting . Аудио каждый участник получает сам; через сеть комнаты передаются управление и метаданные. Участникам нужны обновлённые сборки. Закрытие комнаты освобождает endpoint и встроенный сервер.

`npm run test:rooms-internet` — отдельный сетевой тест с настоящими публичными ретрансляторами. Он запрещает прямые IP-транспорты (`SOSO_ROOMS_RELAY_ONLY=1`), проверяет приглашение, неверный секрет, вход, общую очередь, права ведущего, паузу, выход/возврат и закрытие комнаты. Этот тест не включён в проверки без сети. Проверка настоящих аудиоплееров через этот транспорт: `$env:SOSO_TEST_ROOMS_INTERNET='1'; $env:SOSO_ROOMS_RELAY_ONLY='1'; npm run test:rooms-playback` (PowerShell). Тест на одном ПК с внешним ретранслятором не заменяет проверку на двух физических ПК у разных провайдеров.

## Собственный WebSocket-ретранслятор (для развёртывания)

Прежний WSS-транспорт сохранён для своего сервера через API `mode: relay`. Обычный интерфейс использует автоматический режим выше. Для WSS нужен публичный сервер с TLS:

Запуск на сервере (Linux после нативной сборки):

```sh
./soso-rooms --relay 127.0.0.1:41337
```

Windows:

```powershell
.\build\native\soso-rooms.exe --relay 127.0.0.1:41337
```

Пример конфигурации Caddy, домен должен указывать на сервер:

```caddyfile
relay.example.com {
    reverse_proxy 127.0.0.1:41337
}
```

После этого в плеере укажите `wss://relay.example.com/`. Запускайте процесс ретранслятора под supervisor/systemd, ограничьте доступ и частоту новых подключений на reverse proxy. До публичного запуска нужны нагрузочная проверка, эксплуатационный мониторинг и защита от массового создания комнат. Прототип ограничивает число соединений и комнат, но не заменяет эти меры.

## Сборка и проверка

```sh
npm run build:rooms
npm run test:rooms
npm run test:rooms-ui
npm run test:rooms-playback
npm run build:renderer
```

В Windows используется Rust MSVC + Visual C++ Build Tools с Windows SDK. Скрипт автоматически загружает окружение установленного Visual Studio через `vswhere`. Для альтернативного GNU toolchain поддерживается portable w64devkit в `.tools/w64devkit`; тогда используется установленный `stable-x86_64-pc-windows-gnu` и runtime из Rust. Это локальные инструменты сборки, они не входят в приложение. `SOSO_ROOMS_TOOLCHAIN` позволяет явно выбрать toolchain.

`npm run dev` и `npm run build` собирают Rust автоматически. Готовый бинарник включается в Electron как `resources/native/soso-rooms.exe`.

Интеграционная проверка запускает самостоятельный Rust-ретранслятор и несколько настоящих Rust-клиентов: приглашения, отказ при неверном ключе, полномочия ведущего, очередь, позиция, восемь участников, выход, закрытие комнаты, повторное создание и обрыв ретранслятора. Аудио на разных физических ПК и публичный WSS-сервер требуют отдельной проверки в соответствующей среде.

`test:rooms-playback` запускает два изолированных окна Electron с настоящими AudioProvider/PlaybackEngine, preload и IPC-мостом. Только музыкальный каталог заменён локальным WAV-источником: аудио действительно декодируется и время воспроизведения продвигается. Проверяются создание/вход через формы, неправильное приглашение, пауза, перемотка на паузе, продолжение, одновременное добавление треков, отсутствие импорта личной очереди, удаление ведущим, права гостя, окончание общей очереди, остановка и восстановление контроллера ведущего, повторный вход и разрыв ретранслятора. Звук тестовых окон заглушён, данные пользователя изолированы. Отчёт сохраняется в `scratch/listening-room-playback/report.json`.
