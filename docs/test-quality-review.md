## 1. Высокий приоритет: CI не запускает существующие проверки интерфейса и интеграций

Места: .github/workflows/ci.yml:64; .github/workflows/release.yml:41; scripts/testing/runAllChecks.mjs:19.

CI выполняет форматирование, типы, архитектуру, release metadata и npm test. Release workflow также запускает npm test, затем build и упаковку. Команды из test:all, включая UI interactions, браузерный плеер, аудиопереходы, чувствительность тестов, media, виджет и локальный сценарий входа YouTube, в эти workflows не входят.

Практическое доказательство: отключённая кнопка Play не замечена Node-набором и проходит TypeScript, но обнаруживается уже существующим UI-тестом.

Действие: включить обязательные проверки из test:all в CI и валидацию перед выпуском, избегая повторного запуска одинаковых шагов. Сохранять логи провалов и результаты UI-проверок.

## 2. Высокий приоритет: сервисы проверены лучше, чем их подключение в приложении

Места: src/desktop/main/index.ts:877 (команды LAN), :1038 (media); tests/lanSyncLifecycle.test.mjs:29; scripts/testing/testMediaFileAccess.mjs:13, :35.

У тестов есть реальные положительные и отрицательные случаи для LAN-сервера и MediaFileAccess. Но тесты вызывают сервисы напрямую либо создают собственный main/renderer. Они не доказывают, что настоящий preload вызывает правильный канал, production main регистрирует этот канал, а ответ доходит до интерфейса.

Именно поэтому полная подмена sync:start и media-регистрации на неработающие ответы сохранила все 1160 зелёных тестов. Дополнительная media-проверка Electron также не заметила отключение настоящего main. Этот пробел есть и в тестах, добавленных мной при предыдущем исправлении.

Действие: добавить несколько проверок запуска настоящего приложения с временным профилем и контролируемым сетевым transport. Проверять цепочку UI → preload → IPC → сервис → результат, включая отказ чужому sender и остановку сеанса. Для выбора файла подменять результат системного диалога на границе зависимости, сохраняя настоящую регистрацию IPC и проверку отправителя.

## 3. Средний приоритет: название security-теста обещает больше, чем его утверждения

Место: tests/auditAndSecurityFixes.test.mjs:14.

Проверка «Content Security Policy ... is strict» проверяет наличие meta-тега, отсутствие literal unsafe-eval и наличие media: в двух директивах. Добавление https: к script-src, разрешающее скрипты с произвольного HTTPS-домена, остаётся незамеченным.

Действие: разбирать директивы CSP и проверять допустимые источники script-src, а также проверять блокировку запрещённого скрипта в Chromium. Переименовать текущую проверку по её фактическому узкому контракту. Не считать её доказательством общей безопасности CSP.

## 4. Средний приоритет: проверка фона проверяет DOM и освобождение ресурсов, но не видео

Место: scripts/testing/testBackgroundMemory.mjs:80.

Фикстура переключается на локальный PNG, проверяет количество img/video и удаление элемента при паузе. Нет проверки успешной загрузки выбранного видео, readyState, роста currentTime, восстановления и перемотки. Удаление src видео сохраняет зелёный результат.

Действие: сохранить полезную проверку ресурсов и добавить отдельный сценарий с маленьким локальным видео через настоящий media-протокол: loadeddata, продвижение времени, seek, пауза и восстановление. Проверять отрицательный случай и сохранение разрешения после перезапуска.

## 5. Средний приоритет: проверка production YouTube-клиента не подключена к автоматическому запуску

Место: scripts/testing/testYouTubeProductionClient.mjs:1.

Скрипт существует и проверяет адаптер в dist-electron после сборки, включая сохранение методов формата. Его нет в package.json, test:all и workflows. Следовательно, обычные зелёные тесты и сборка не гарантируют выполнение этой проверки.

Действие: запускать скрипт после build перед упаковкой/выпуском; отдельно добавить команду npm. Не запускать его до сборки по устаревшему dist.

## Ограничения и следующий приоритет

Это целевая проверка чувствительности, а не полный mutation campaign и не измерение line/branch coverage. Автоматические статические категории из inventory.json носят диагностический характер; наличие readFileSync само по себе не означает проверку строк — часть тестов исполняет прочитанный production-код через VM.

Сначала стоит подключить существующие UI-проверки к CI, затем закрыть production IPC/bootstrap и видеофон, подключить production-проверку после сборки и усилить CSP-тест. После этого имеет смысл искать дубли по покрываемым сценариям и запускать более широкий mutation testing. Само уменьшение количества тестов найденные пробелы не исправит.

Артефакты: scratch/test-audit/inventory.json, mutation-results.json, extended-results.json и логи отдельных запусков. В них сохранены конкретные команды, коды завершения и сообщения ошибок.
