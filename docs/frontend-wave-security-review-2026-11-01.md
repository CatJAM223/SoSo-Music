# Анализ интерфейса, волны и безопасности — 1 ноября 2026

Изменений кода и сборки в рамках анализа нет. Проверены текущие исходники, выполнены три изолированные проверки в памяти. Полного пентеста, проверки CVE зависимостей и замеров кадров на пользовательском профиле не проводилось. Ниже подтверждённые свойства кода отделены от предполагаемых последствий и проектных предложений.

## Безопасность

### S1 — Medium: неодинаковые полномочия окон через IPC

Доказательства: `src/desktop/main/index.ts:313` и `:411` загружают один preload в основное окно и виджет; `src/desktop/preload/index.ts:151` предоставляет getWaveBatch. Обработчики `src/desktop/main/ipc/waveHandlers.ts:14`, `libraryHandlers.ts:55`, `playlistHandlers.ts:42` не проверяют отправителя. В `mainWindowHandlers.ts:3` уже есть проверка и WebContents, и главного frame, но применяется она выборочно.

Последствие: при компрометации менее привилегированного окна доступные ему методы могут менять библиотеку и запускать ресурсоёмкую работу. Само наличие удалённого пути компрометации/XSS не установлено; это подтверждённый дефект границы полномочий, не доказанное удалённое выполнение кода.

Предложение: минимальный preload для виджета, серверные проверки отправителя у всех привилегированных операций. Не полагаться исключительно на отсутствие кнопки в интерфейсе. Руководство Electron: https://www.electronjs.org/docs/latest/tutorial/security/#17-validate-the-sender-of-all-ipc-messages

### S2 — Medium: обход лимита запросов волны без requestId

Доказательство: `src/desktop/main/services/waveBatchRequestRegistry.ts:16` возвращает незарегистрированный контроллер, когда requestId отсутствует. Проверка восьми запросов находится ниже, на строке 31. Изолированная проверка приняла 20 незавершённых вызовов без ID. Для этой ветки также отсутствует отмена при уничтожении окна.

Последствие: вызывающий с доступом к IPC может размножать незарегистрированные задачи. Сетевой scheduler по-прежнему ограничивает параллелизм и очередь: это не утверждение о неограниченных одновременных HTTP-запросах.

Предложение: учитывать все операции, генерируя внутренний ID для старых клиентов; общий лимит на окно и обязательная отмена при его закрытии.

### S3 — Medium: проверка размеров входных данных происходит после части обработки

Доказательство: `src/desktop/main/ipc/waveHandlers.ts:47` вызывает filter/map на learnedTracks до normalizeWaveBatchContext; строка 56 фильтрует tasteTracks до обрезки. excluded копируется без локального предела. Статические типы TypeScript не проверяют IPC во время исполнения.

Последствие: объект вместо массива вызывает исключение, большие массивы дают лишнюю работу в основном процессе. Возможность устойчивого отказа в обслуживании не измерялась. Требуется доступ к соответствующему IPC.

Предложение: сначала форма, допустимые значения, длины и ограничения массивов; затем обращения к БД и обработка. Снимок tastePolicy получать один раз, а не для каждого элемента.

Подтверждённые защиты: sandbox/contextIsolation/webSecurity основного окна включены; Node integration выключен. В комнатах есть лимит 64 TCP-соединения, 32 входящих интернет-сессии, 8 участников, 20 треков, кадры до 64 KiB и таймауты. Обложки при преобразовании в обычные треки проходят safeRoomArtwork. Эти места не считаются обнаруженными уязвимостями.

## Баги и несогласованность алгоритмов

### B1 — смешение достоверности тегов

`src/desktop/main/services/libraryTaste.ts:233`: теги артиста объединяются с тегами трека, а waveMetadataScope выставляется на весь набор. Если у трека уже есть жанр, весь объединённый набор получает scope=track.

Воспроизведение: трек genre=ambient имел energy=-1; после добавления artist fallback metal получил energy=0 и scope=track. Значит, осторожное отношение к тегам артиста можно потерять при объединении. Нужны происхождение и вес каждого признака, а не одна метка на весь трек.

### B2 — слабые признаки всё ещё дают сильный штраф перехода

`waveMusicProfile.ts:99` уменьшает энергию artist scope до четверти. Но `native/compute-core/src/ranking.rs:43` проверяет только знак произведения энергий. Слабые +0.25/-0.25 считаются противоположностью, как +1/-1, и получают тот же штраф перехода. Аналогичное сравнение знака используется в similarity в sequence.rs. Требуется единое применение уверенности во всех частях оценки.

### B3 — переключение без прослушивания вызывает обновление волны

`src/shared/services/waveRefreshPolicy.ts:18` допускает seconds=0. Для трёх разных ID вызов observe(id,0,180,'skip') вернул false,false,true. При этом Rust wave_feedback игнорирует прослушивание менее 0.5 секунды. Это может запускать ненужные запросы при быстром пролистывании ещё не загрузившихся треков. Обновление каталога и оценка вкуса должны согласованно различать навигацию и реальное прослушивание.

## Оптимизации, которые стоит измерить

- **Кеш профиля зависит от всех сохранений БД.** waveTasteSnapshot.ts:33 использует общий getChangeRevision; db/index.ts:359 увеличивает его в save, в том числе при записи истории. Полезна отдельная ревизия данных вкуса и объединение частых обновлений. Нельзя просто увеличить TTL: исключения и дизлайки должны действовать сразу.
- **Повторное чтение политики внутри фильтров.** waveHandlers.ts:37/48/56 заново получает policy для каждого трека. Один снимок на обработку запроса уменьшит число чтений и сохранит согласованность.
- **Большая очередь полностью создаёт DOM.** QueueDrawer.tsx:283 отображает upcomingItems.map без виртуализации. Для больших обычных плейлистов стоит измерить открытие и перетаскивание на 1000+ треков и добавить окно видимых строк. Двадцатитрековой комнате это почти ничего не даст.
- **Общий React context.** TrackRow использует useAudioState; React.memo не изолирует от обновлений самого context. Измерить обновления видимых строк при смене трека/лайка и перейти к выборочным подпискам там, где есть заметная стоимость.
- **Матрица сравнений O(n²).** sequence.rs:380 вычисляет обе половины симметричной матрицы. Можно вычислять половину и зеркалировать; для очень больших пулов — сначала индексировать подтверждённые recordingId и группы возможных совпадений. Нельзя подменять точную проверку одним названием.
- **Синхронное сохранение памяти волны.** waveMemory.ts:99 сериализует played/offered в localStorage, во время прослушивания — с интервалом около 10 секунд. На крупной истории измерить длительность, затем объединять записи либо сохранять асинхронно. Полезно проверить сохранность при аварийном закрытии.

Ни для одного из этих пунктов не заявляется измеренное ускорение: текущий проход не включал профилирование.

## Развитие алгоритмов волны

1. **Разнообразие по звучанию на окне очереди.** Сейчас есть сильное разнесение артистов и оценка перехода от предыдущего трека. MMR можно применить к последним 5–10 песням: учитывать релевантность вкусу и штраф за музыкальную похожесть, а не только совпадение артиста. Ограничить силу штрафа для тематических режимов. Перенос идеи на музыкальные признаки — предложение, не результат эксперимента в этом проекте. Источник: https://www.cs.cmu.edu/afs/cs/Web/People/jgc/publication/MMR_DiversityBased_Reranking_SIGIR_1998.pdf
2. **Несколько направлений вкуса вместо одного общего набора.** Группировать любимую музыку по стилям/признакам и выбирать направление текущей сессии. Последние успешные прослушивания меняют направление, но не стирают долгосрочные предпочтения. Не переключать жанр после единственного пропуска.
3. **Адаптивный выбор способа поиска.** Контекстный бандит может выбирать между радио по треку, похожими артистами, жанровым поиском и знакомым каталогом. Награда — осмысленное прослушивание и сохранение, с отдельным учётом ошибок источника. Сначала небольшой ограниченный эксперимент; локальных данных может быть мало. Источник: https://arxiv.org/abs/1003.0146
4. **Уверенность в предпочтении должна доходить до Rust.** В wavePreferences strength используется для отбора/порядка, но learnedTracks возвращает Track без численного веса. sequence.rs:137 использует максимальное сходство learned-профилей. Слабое и многократно подтверждённое предпочтение поэтому могут давать одинаковый музыкальный вклад. Передавать ограниченный вес и давность доказательства.
5. **Две независимые оси новизны.** Новая песня любимой группы и новый исполнитель — разные эксперименты. Текущие значения 0/0.5/1 всё ещё сводятся в единую поправку discoveryAdjustment. Нужны разные счётчики и квоты, чтобы неудачная песня знакомой группы не уменьшала автоматически шанс открыть нового артиста.
6. **Надёжность источника отдельно от музыкального вкуса.** Короткий cooldown сломанного provider ID и выбор рабочей копии той же записи. Ошибка потока не должна портить отношение к артисту. Не исключать весь трек навсегда из-за временной ошибки CDN.
7. **Проверка улучшений.** Версии ранжирования, сопоставимые сессии, ранние пропуски среди реально начавшихся треков, дослушивания, лайки открытий, покрытие артистов и ошибки старта. Не считать отсутствие прослушивания отрицательной оценкой и не обещать выигрыш на основании чужого эксперимента.

## Фронт: поведение и анимации без перестановки элементов

- Единые длительности и кривые: короткий отклик на нажатие, чуть более длинные перемещения/появления. Вынести повторяющиеся значения в motion tokens; менять opacity/transform, не анимировать всё подряд.
- Смена обложки через декодирование следующего изображения и короткое перекрытие со старым. Сейчас keyed img получает входную анимацию, но сама по себе она не гарантирует готовность картинки. При быстрых переключениях отменять устаревший переход.
- В очереди показывать смещение соседей во время drag, место вставки, плавное схлопывание удалённой строки и возможность отменить удаление. Стабильный queueEntryId обязателен при дублирующихся песнях.
- После добавления в комнату: короткая смена значка на галочку, мягкое появление подсветки и состояние ожидания подтверждения. Не добавлять текстовые бейджи, которые пользователь уже попросил убрать.
- Перемотка: визуально различать выбранную позицию и ожидание звука; при реальном буферинге не рисовать фиктивное движение времени. Нынешний живой прогресс уже есть, повторно его реализовывать не нужно.
- Поиск: сохранять предыдущую выдачу до готовности новой, показывать неброский индикатор работы; отменять устаревшие запросы и не проигрывать входную анимацию всей таблицы при каждом символе.
- Комнаты: понятные состояния подключения, подготовки и восстановления связи; индикатор должен отражать состояние, а не просто бесконечно вращаться.
- Всплывающие элементы: согласованные вход/выход, Escape, возврат фокуса в кнопку-источник, отсутствие невидимых активных кнопок при закрытии.
- Учесть reduced-motion, скрытое окно и длинные списки. Проверять p95 времени кадра и задержку до визуального отклика. Анимации не должны задерживать само действие.

Приоритет работы: S1–S3 и B1–B3; затем измерения очереди/профиля, обратная связь на действия, затем ограниченные эксперименты с алгоритмами.


## Статус исправлений

Подтверждённые S1–S3 и B1–B3 исправлены в исходниках: общий запрет IPC для посторонних окон и дочерних frame, минимальный API виджета, учёт запросов без ID, проверка контекста до обработки, единый снимок политики на запрос, сохранение музыкальных признаков трека при artist fallback, пропорциональный штраф за неуверенные признаки в Rust и исключение навигации до 0.5 секунды из обновления каталога. Предложения по новым алгоритмам и анимациям остаются предложениями; этот статус не утверждает отсутствия любых возможных уязвимостей.
